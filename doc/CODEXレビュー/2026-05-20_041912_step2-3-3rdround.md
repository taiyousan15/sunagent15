### HIGH-1 — `lastUpdated` だけを optimistic version にしているため、同一 timestamp では stale save が通り、2nd-round の lost update が残る

File: `/Users/matsumototoshihiko/Desktop/dev04/sunagent15/src/memory/MemoryService.ts:958`, `/Users/matsumototoshihiko/Desktop/dev04/sunagent15/src/memory/MemoryService.ts:986`, `/Users/matsumototoshihiko/Desktop/dev04/sunagent15/src/memory/MemoryService.ts:995`, `/Users/matsumototoshihiko/Desktop/dev04/sunagent15/src/memory/MemoryService.ts:1013`

Issue: 258a959 の stale check は `onDisk.lastUpdated !== stats.lastUpdated` だけを stale 判定にしている。ところが保存側も `new Date().toISOString()` を `last_updated` に書き戻すだけなので、ロック内の先行書き込み後も timestamp 文字列が進まない場合、後続の stale snapshot は「同じ version」と誤判定されて保存される。

Evidence: 固定時計で同じ `lastUpdated` を返す状態にして、2nd-round と同じ sequence を再現した。

1. `svcA.recordTask(t1)`
2. `const stale = svcA.loadAgentStats(agent)`
3. 同じ timestamp のまま `svcB.recordTask(t2)`
4. `svcA.saveAgentStats(stale)`

結果は `threw:false`, final `totalTasks:1`, final ids `["t1"]`。つまり `t2` は消えた。これは通常時計の必須 4-step repro が通ったこととは別で、現在の optimistic token が「変更の有無」ではなく「時計文字列が変わったか」に依存しているために起きる。

Impact: public `saveAgentStats(stats)` の load-modify-save 利用者は、同一 timestamp で先行する `recordTask()` の更新をまだ消せる。データ消失であり、2nd-round HIGH の根本条件を満たしていないため release-quality GO にはできない。

Suggested fix: stale 判定の version token を衝突しないものにする。例: runtime YAML に単調増加 `revision` / `version` を持たせて lock 内で必ず increment する、または保存時に「直前に読んだ file hash / revision」を比較する。少なくとも `saveAgentStatsLocked` は同じ agent の既存 `lastUpdated` と同じ値を書かないよう、lock 内で strictly monotonic に進める必要がある。固定時計で `recordTask(t2)` 後の stale public save が必ず throw し、final が `totalTasks === 2` かつ `t1/t2` 両方保持になる regression test を追加すること。
