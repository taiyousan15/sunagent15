## 5. 設計判断と根拠

1. **doc 系もパス変更**: agent-source は LLM(エージェント)が読む指示書。説明文と bash の path を揃えないと、LLM が説明文を根拠に legacy path の bash を再生成しうる。整合性のため全箇所 runtime 化。
2. **mkdir -p 追加（reflection L512）**: runtime ディレクトリは通常 MemoryService/installer が作るが、bash fallback が単独最初に走るケースで `cat > "$STATS_FILE"` が ENOENT で失敗する。`mkdir -p` で堅牢化。副作用なし（既存なら no-op）。
3. **cold-start で baseline manifest を bash から読まない**: manifest が持つのは calibration の**下界値**（min_success_rate 等）で、scoring に使う**実績** success_rate ではない。実績なしなら 0.85 中立値が意味論的に正しい。manifest seeding は MemoryService(TS)の責務（OPEN-1 RESOLVED 済）で、bash に重複実装しない。
4. **MemoryService API 経由でなく runtime path 直書き**: bash から TS(node/tsx)を呼ぶのは重く、依存(yq)前提の現行 fallback の趣旨に反する。PLAN L69 も「point to `.claude/agent-memory/agents/`」を明示的に許容。

## 6. Codex への論点（事前レビュー依頼事項）

2. **mkdir -p 追加**: reflection L512 の堅牢化は妥当か。`.locks`/atomic は bash では扱わない判断でよいか。
3. **CI rule 正規表現の精度**: `_template.yaml` 誤許可 / `${...}-stats` 等の見逃しはないか。glob `--glob '.claude/agent-source/**'` の指定方法は正しいか。
