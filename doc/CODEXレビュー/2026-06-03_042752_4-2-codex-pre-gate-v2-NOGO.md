## 技術2件（ACCEPT・plan v3で修正）
1. **EOVERRIDE（finding 2・実測確認）**: voice-ai `ws:^8.18.0`/`uuid:^11.0.0`、ai-sdr `uuid:^11.0.0` は **direct dependency**（`node -e` で確認）。これらを overrides に書くと npm が EOVERRIDE で失敗。
   → **修正**: ws(voice-ai)・uuid(両) は `dependencies` の spec を直接 bump（ws→`^8.20.1`、uuid→`^11.1.1`）。transitive な axios/ajv/@hono/node-server/path-to-regexp(scoped)/express-rate-limit(ai-sdrのみ・voice-aiは直接ゆえ既に安全) は override 継続。
2. **shell flow（finding 3/4・ACCEPT）**: `set -e` 下では `verified_update; rc=$?` は失敗時 rc 取得前に exit → `if verified_update; then ... else ... fi` に変更。`trap - RETURN` 前に明示 `rm -rf` するか cleanup を確実化。

## MUST-3 / finding 1（DIVERGE → ユーザー判断）
- **Codexの主張**: release品質には「検証付きを既定」が必須。opt-in（既定=無検証 mutable main）は NO-GO。MUST-fix=「実 release(tar.gz+.sha256) を公開し同時に既定を verified に flip」。
- **Opus の反論（根拠）**:
  1. release 公開は **タグ push + CD 実行**が必須 → ユーザーの **commit-only / no-push 指示と衝突**。
  2. 「どう配布/公開するか」は **4-3 配布設計（plugin/ZIP/private 等）をユーザーが保留中**＝FIX-9 の secure-default は配布モデル決定に**依存（entangled）**。public/private も未定。
  3. opt-in 追加は**非回帰**（検証経路を“足す”だけ・既定挙動は不変＝悪化なし）。release品質の理想ではないが、interim improvement としては有効。
- **結論**: FIX-9 の「検証既定」は本 commit-only PR では**実現不能**（ユーザーの保留事項に依存）。→ codex.md rule#3 によりユーザーに判断を仰ぐ。
