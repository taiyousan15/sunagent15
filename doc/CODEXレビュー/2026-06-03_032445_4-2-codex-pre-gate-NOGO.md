## MUST-fix と Opus の accept/reject（実測検証つき）

### 1. vitest を「据置き＋明記」は不可 → **ACCEPT**（Opus の前提が誤り）
- Codex指摘: nested の install/update は `npm ci`/`npm install` を **`--omit=dev` なし**で実行＝devDependencies がユーザー機にインストールされる。`files:['dist']` は npm publish 用で source-tree install には無関係。
- **Opus 実測検証**:
  - `scripts/install.sh:336/338` `NPM_INSTALL_CMD=(npm ci)` / `(npm install)`、`:379/381` per-MCP `npm ci/install` — **`--omit=dev`/`--production`/`NODE_ENV` 無し**。
  - `scripts/update.sh:140` `npm ci ... || npm install`、`:158/160` per-MCP 同様 — **`--omit=dev` 無し**。
  - `mcp-servers/*/package.json` に `"vitest": "^3.0.0"`（devDependencies）＋ `"test": "vitest run"`。
  - → **vitest と脆弱な依存(postcss/picomatch/vite/rollup)はユーザー機に実際にインストールされる**。session48 で Opus がユーザーに説明した「vitestは出荷物に入らない・発火しない」は**誤り**。（CVE本体は @vitest/ui 必須で未インストールゆえ当該exploit経路は塞がっているが、「既知CRITICALがインストールツリーに残る」はリリース品質ではない、という Codex の主張が正当）
- **対応**: vitest を両 nested の devDependencies から**削除**して lockfile 再生成（`test`スクリプトも無効化/除去）。または install/update を `--omit=dev` 化。前者推奨（テスト0個ゆえ破壊なし＋critical/dev系highを一掃）。

### 2. FIX-9 検証付き更新が release install で到達不能 → **ACCEPT**
- Codex指摘: `update.sh` は `.git` 無しだと更新前に exit。`install-release.sh` は .git を作らず tar 展開のみ。＝安全インストール経路が安全更新経路を使えない。
- **Opus 実測検証**: `scripts/update.sh:41-44` `if [ ! -d "$REPO_DIR/.git" ]; then echo error; exit 1; fi`（**.git無しは即exit 1**）。`install-release.sh:117` `tar -xzf ... --strip-components=1`（.git作らず）。→ release archive 導入ユーザーは update.sh を**全く実行できない**。update.sh内に検証モードを足す案は彼らに届かない。
- **対応**: 検証経路を **.gitゲートの前に分岐**し、非git（release archive）導入にも対応する設計に再構成。

### 3. FIX-9 既定が mutable-HEAD のままは不十分 → **ACCEPT**（Opus blind でも最弱点と指摘）
- **Opus 実測検証**: root `install.sh:19/99/108`（main HEAD を clone/reset）、`update.sh:69/86`（`git pull origin main`／`main.zip` フォールバック）。無検証パスが標準のまま。
- **対応**: 検証付き（release tag + .sha256）を**既定**化し、mutable main/ZIP は明示的 unsafe opt-in に。OWASP Software Supply Chain Security Cheat Sheet 準拠。

### 4. 検証後も fail-closed でない（npm ci→install フォールバック）→ **ACCEPT**
- **Opus 実測検証**: `update.sh:140` `npm ci ... || npm install`、`install.sh:341`(+`--allow-partial`継続)。lockfile不一致時に黙って再解決＝frozen性が壊れる。
- **対応**: 検証付き更新ブランチでは `npm install` フォールバック禁止（`npm ci` 失敗は abort）。

### 5. (MEDIUM) override マトリクス未記載 + path-to-regexp スコープ → **ACCEPT**
- **Opus 実測検証**: `voice-ai lock:2006` `path-to-regexp ~0.1.12`（express@4配下）と `:2925` `^8.0.0`（express@5配下）が**併存**。blanket `overrides:{path-to-regexp:"8.4.2"}` は express@4 を 8系に強制＝**ルーティング破壊（Pattern 8）**。
- **対応**: 計画に**正確な scoped override マトリクス**を明記。path-to-regexp は版別（0.1系→0.1.13 / 8系→8.4.2）。安全には非破壊 `npm audit fix`（版別に解決）か nested scoped override を使用。

### 6. (MEDIUM) FIX-3b 除外の根拠不足 → **ACCEPT（精緻化）**
- **Opus 実測検証**: E404の `n8n-mcp`(:156 `disabled:false`)・`facebook-ads-library`(:236 `disabled:false`)等が**既定で有効**。よって「bare維持＝起動安全」は証明になっていない（有効かつE404＝既に壊れている可能性／別経路解決の可能性）。uvx 除外も「スコープ削減」であって supply-chain 閉鎖ではない（未ピンPyPIランチャが既定で実行される）。
- **対応**: (a) E404 6種は別件の正しさ調査（本当に起動するのか）に切り出すと明記。(b) uvx 5種は `pkg==ver` ピンを検討（少なくとも残リスクを SECURITY に明記）。local node 除外は妥当（repo-pinned）。

### 7. (LOW) sink 第二sink → Codex も「無し」を確認（Opus blind と一致 AGREE）
- `listTabsViaCDP` の消費先は本pipelineと skills.ts のみ。skills.ts は session46で sanitize 済。下流normalizeはurl/hrefのみ抽出。→ :219 の sink fix で十分。
