## Findings

### HIGH-1

File: `src/memory/MemoryService.ts:300`, `src/memory/MemoryService.ts:320`, `src/memory/MemoryService.ts:325`, `src/memory/MemoryService.ts:683`, `scripts/memory-report.ts:100`

Issue: The nested `omega_metrics`, `learning_metrics`, and `metadata` YAML trees are passed through as-is into the camelCase `AgentStats` type. The shipped legacy files are canonical snake_case, so `metadata.overallHealth` is undefined after `loadAgentStats()`, and `generateSummaryReport()` calls `agent.health.padEnd(8)`.

Impact: A normal production command, `npx ts-node scripts/memory-report.ts summary`, crashes on the repository's shipped `.claude/memory/agents/*-stats.yaml` files. This is not just a test concern; reports and any typed consumers of `AgentStats.metadata`, `omegaMetrics.dependencies.dependenciesList`, or `learningMetrics.specialization.primaryCategory` are reading the wrong shape.

Suggested fix: Implement OPEN-1 now. Add explicit decode/encode mappers for all nested stats: snake_case YAML to camelCase `AgentStats`, and camelCase `AgentStats` back to snake_case YAML. Extend Step 9(l) to assert both on-disk YAML and typed `loadAgentStats('api-designer')` access. The skipped deep-equality test in `tests/integration/memory.integration.test.ts:528` should be enabled or replaced with mapper-specific tests.

### HIGH-2

File: `src/memory/MemoryService.ts:1007`, `src/memory/MemoryService.ts:1010`, `src/memory/MemoryService.ts:1011`, `src/memory/MemoryService.ts:1026`, `src/memory/MemoryService.ts:1027`

Issue: `recordTask()` creates an empty stats file before acquiring the per-agent lock. That check-then-write is outside the lock and uses truncating `fs.writeFileSync(path, '')`, so two first writers can interleave such that one process truncates a real stats file written by another process under lock.

Impact: First-use concurrent `recordTask()` for the same agent can lose tasks or leave the runtime file temporarily empty. Even without concurrency, every first-use `recordTask()` creates an empty file, then immediately reads it as corrupt and quarantines it; the targeted Jest run showed these warnings for normal successful tests.

Suggested fix: Remove the placeholder write. With `realpath: false` and `lockfilePath`, `proper-lockfile@4.1.2` can lock a non-existent target path; I verified this locally. Acquire the lock first, then create or write the stats file only through the locked load-update-save path. Add a multi-process first-writer test that asserts two simultaneous new-agent `recordTask()` calls persist both tasks and create no `.corrupt` placeholder quarantine.

### HIGH-3

File: `src/memory/MemoryService.ts:871`, `src/memory/MemoryService.ts:903`, `src/memory/MemoryService.ts:1198`, `src/memory/MemoryService.ts:1204`, `src/memory/MemoryService.ts:1214`

Issue: `saveAgentStats()` is public and unlocked, and `cleanupOldTasks()` loads all agents, mutates stale in-memory objects, and writes them through `saveAgentStats()` without acquiring the per-agent lock.

Impact: `cleanupOldTasks()` can overwrite a concurrent `recordTask()` update: cleanup reads stats, recordTask locks and saves a new task, then cleanup writes its stale copy outside the lock. This is exactly PLAN.md OPEN-2 and is a data-loss race, not a theoretical style issue.

Suggested fix: Centralize mutation in a `withAgentStatsLock(agentName, fn)` / `mutateAgentStats()` helper. `recordTask()`, `cleanupOldTasks()`, and any public save path should acquire the same lock, invalidate cache, re-read under lock, apply changes, and save before release. If raw `saveAgentStats()` must remain public, document it as unsafe or make it private and expose only locked mutation APIs.

### MED-1

File: `tests/integration/memory-separation.integration.test.ts:497`, `tests/integration/memory-separation.integration.test.ts:506`, `tests/integration/memory-separation.integration.test.ts:518`, `tests/integration/memory-separation.integration.test.ts:521`

Issue: Step 9(k) claims concurrency coverage, but the tests are serial calls in one process or two service instances in the same process. They do not exercise simultaneous multi-process lock contention, first-writer races, or stale-lock recovery.

Impact: The placeholder race in HIGH-2 and the unlocked cleanup race in HIGH-3 are not covered. The lock can look correct while the production interprocess behavior remains unsafe.

Suggested fix: Add a child-process or worker-based test with a barrier so multiple processes call `recordTask()` against the same empty runtime agent at the same time. Assert final `total_tasks`, `recent_tasks`, absence of `.corrupt` placeholder files, and lock release. Add a separate `cleanupOldTasks()` + `recordTask()` race regression for OPEN-2.

### MED-2

File: `tests/integration/memory-separation.integration.test.ts:537`, `tests/integration/memory-separation.integration.test.ts:576`, `tests/integration/memory-separation.integration.test.ts:582`, `tests/integration/memory-separation.integration.test.ts:599`

Issue: The PR-beta blocking manifest test creates a synthetic one-entry manifest instead of using the actual tracked `.claude/memory/agents-baseline.yaml`, and it asserts only on serialized YAML, not typed `AgentStats`.

Impact: The test does not prove the real 48-entry manifest can seed a real agent correctly after PR-beta, and it intentionally misses the typed-object failure in HIGH-1. A same-shape synthetic fixture can pass while production report paths crash.

Suggested fix: In addition to fixture tests, add an integration test that points `MemoryService` at a copied real `.claude/memory/agents-baseline.yaml`, removes legacy/runtime stats, records `api-designer`, and asserts both canonical YAML and typed access such as `stats.omegaMetrics.dependencies.dependenciesList.tools` and `stats.metadata.overallHealth`.

### LOW-1

File: `src/memory/MemoryService.ts:951`, `src/memory/MemoryService.ts:962`, `src/memory/MemoryService.ts:965`

Issue: `atomicWriteFile()` fsyncs the temporary file before `renameSync()`, but it does not fsync the parent directory after the rename.

Impact: On POSIX filesystems, file content is flushed, but crash durability of the directory entry is not fully guaranteed. This is PLAN.md OPEN-5 and is unlikely to corrupt YAML, but a power loss can still lose the new name.

Suggested fix: After `renameSync(tmpPath, targetPath)`, open the parent directory read-only and `fs.fsyncSync(dirFd)` where supported. Add a Windows fallback/comment because directory fsync semantics differ.

### LOW-2

File: `src/memory/MemoryService.ts:30`, `src/memory/MemoryService.ts:128`, `src/memory/MemoryService.ts:129`, `PLAN.md:322`, `PLAN.md:324`

Issue: Runtime slug validation only enforces `^[a-zA-Z0-9_-]+$`, while the baseline generator hardens slug validation with a Windows reserved-name denylist and hyphen-shape rules.

Impact: Runtime can create agent slugs that the manifest generator or future CI rejects, causing runtime/manifest parity drift. The current filename suffix makes most Windows device-name cases less dangerous than raw filenames, so this is not blocking, but the validator does not actually match the claimed generator parity.

Suggested fix: Share a single slug validation rule between `MemoryService` and `scripts/generate-agents-baseline.js`, including the denylist and hyphen rules, or explicitly document why runtime accepts a broader set.

### LOW-3

File: `src/memory/MemoryService.ts:341`, `src/memory/MemoryService.ts:342`, `src/memory/MemoryService.ts:343`

Issue: Corrupt-file quarantine filenames use only millisecond timestamp precision and `renameSync()` directly to that path.

Impact: Two corrupt reads for the same agent in the same millisecond can collide. On POSIX, rename can overwrite the earlier quarantine; on Windows it may fail. This is rare, but it weakens forensic value exactly when corruption is being investigated.

Suggested fix: Add PID + random bytes to the quarantine filename, or loop with an exclusive create / exists check before renaming.
